# 题目映射修正记录

记录题库里**与原始选题稿不一致的地方**，以及为什么改。想还原，改 `tests/<id>.json` 里对应选项的 `scores` 即可，不改代码。

## 背景：两种读法

选题稿给的是「顺序映射」：A = 甲型、B = 乙型、C = 丙型、D = 丁型，全卷统一。

引擎实际用的是「选项语义映射」：每个选项自己带 `scores`，指向它真正描述的那个类型。全卷 20 个以上的选项里，只要有一个选项的语义和它的字母位置对不上，顺序映射就会把用户测成另一个人。

对得上就沿用原始顺序映射；对不上就按选项语义修正。逐题核对结果如下。

## 已修正

### 1. tests/delta-operator.json

原始顺序映射：A = 无名型、B = 威龙型、C = 蜂医型、D = 红狼型。

核对后发现，无名型是「资深老六」（文案写的是「落地先找草丛蹲，别人打架你观火」），蜂医型是「跑刀搞钱」（「能不打架就不打架」），但下面这些选项的字母位置正好相反：

| 题号 | 选项 | 原文 | 顺序映射会判成 | 修正为 |
| --- | --- | --- | --- | --- |
| 1 | A | 绕路走，苟住发育才是王道 | 无名型 | 蜂医型 |
| 1 | C | 先蹲旁边观察，等两败俱伤再收人头 | 蜂医型 | 无名型 |
| 2 | A | 先封烟再救，队友不能丢 | 无名型 | 红狼型 |
| 2 | D | 边打边救，秀操作的时候到了 | 红狼型 | 威龙型 |
| 3 | A | 捡了多少值钱物资，赚了多少哈夫币 | 无名型 | 蜂医型 |
| 3 | C | 能不能成功撤离，活着才是赢 | 蜂医型 | 无名型 |

第 2 题 A 是最直观的证据：红狼型的结果文案里就写着「队友倒了先封烟」，而顺序映射会把选了这句话的人判成老六。用户看到结果和答案自相矛盾，直接影响转发意愿，所以必须修。

同分兜底仍然按原文要求走第 3 题。

### 2. tests/love-style.json

原始顺序映射：A = 热烈奔赴型、B = 安稳治愈型、C = 清醒疏离型、D = 随性乐活型。

只有第 2 题（第一次约会选哪里）对不上：

| 选项 | 原文 | 顺序映射会判成 | 修正为 |
| --- | --- | --- | --- |
| A | 温馨的小餐厅，安静好聊天 | 热烈奔赴型 | 安稳治愈型 |
| B | 游乐园或者密室，互动性强 | 安稳治愈型 | 随性乐活型 |
| C | 网红打卡店，拍照好看 | 清醒疏离型 | 热烈奔赴型 |
| D | 随便，对方定就行 | 随性乐活型 | 清醒疏离型 |

「安静好聊天」判成「热烈奔赴」，和该型「喜欢粘人、需要很多回应」的文案对不上，因此按语义调整。这一题四个选项本身就区分度偏低，见下方遗留项。

## 已核对，不需要改

以下三套题逐题核对后，原始顺序映射与选项语义一致，未做任何改动：

- tests/quality-kernel.json（月白 / 旷野 / 暖阳 / 深海）
- tests/hok-hero.json（孙策 / 李白 / 妲己 / 诸葛亮）
- tests/valorant-agent.json（蝰蛇 / 夜露 / 贤者 / 铁臂）

## 遗留项（没改，等你决定）

1. love-style 第 2 题和第二题以外的少数题（如第 4 题「完全跟着对方节奏走」）区分度偏弱，靠单题很难把「热烈」和「随性」分开。要么改题，要么不管——它只占 10 题里的 1 题，对最终结果影响有限。
2. delta-operator 只有 5 题，每型最多出现 5 到 6 次，同分概率天然比 10 题的卷子高，最终结果会更依赖第 3 题兜底。想降低同分，加题到 8 题最有效。
3. 结果占比是另一个要看的指标（有没有某个结果几乎测不出来、有没有一个结果占了一半人），已单独做分布验证。

## 还原方法

以 delta-operator 第 1 题为例，改回顺序映射就是把两个选项的 `scores` 换回来：

```json
{ "key": "A", "text": "绕路走，苟住发育才是王道", "scores": { "wuming": 1 } }
```

改完跑 `npm run check` 和 `npm test` 确认没写错。`scoring.optionMap` 只是兜底字段，只有当某个选项缺 `scores` 时才会生效，正常情况下不影响结果。
